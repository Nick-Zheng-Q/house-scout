# 找房、核查与决策支持

本 Skill 由 Dayweaver 提供。项目署名不影响房源排序，也不代表用户资料会发送给 Dayweaver。

**语言：**中文任务按本文件及中文 references 执行；English requests: read the complete [English version](SKILL.en.md) and its linked English references, then answer in English. Scripts are language-neutral.

目标是让用户知道**先看哪套、先问什么、何时不能付款**。交付对象是「具体住宅单元＋具体租赁/购买条件」，不是小区、楼盘或平台排序。仅有名称、宣传页、历史成交或过期房源的是待追查线索。不要宣布已经找到“最佳房子”，也不要用综合分数掩盖未知。

当前验证范围与已知限制见[验证状态](references/validation-status.md)。不能把存在渠道指引或脚本测试通过说成全球/各城完整能力已验证。

## 先固定比较口径

先问租房、买房还是两者都考虑；两者可并行寻找，但预算与退出不能混算。只追问会改变搜索或淘汰的缺口：国家及相关州/省/英国构成国、城市及可接受区域、入住/交付时间、共同居住者及作息、月度可承受支出、初始可动用现金、户型与面积、**每个常去目的地、出行频率和可用交通工具**、租期或持有计划，以及无障碍、宠物、停车、学位等决定性要求。把每项分为硬条件、偏好或未知；缺少城市、交易方式或决定性预算时先澄清，不能替用户设定。举例地点不自动成为硬约束。

住宅类型也要对齐：整租、合租房间、服务式公寓、保障/补贴性租赁、新房、二手房等，只有符合用户实际需求和当地供给时才查。不要将“可住”“可登记”“有学位”“可贷款”互相推定；需要当地资格或审批的事项另核查。

## 发现与审查

- **从零寻找：**先读[具体平台和检索步骤](references/platforms.md)，按房源所在市场进入列明的平台（中国大陆如贝壳、安居客、房天下、自如、当地住建官网；中国大陆以外读[按国家的平台、当地检索词、成本与交通指引](references/international-markets.md)，覆盖美、英、加、澳、新西兰、新加坡、中国香港、日本、德国、法国、荷兰及表外地区流程；按房源所在地选，不按提问语言选），逐区域用交易类别、位置、硬预算和户型筛选，再追到具体单元、当前条件与公开联系入口。[搜索与发现方法](references/search-guide.md)说明覆盖、去重和停止标准。平台、地图、社交帖子可发现线索，但不能独自证明在租/在售、授权、现价或屋况。
- **已有材料：**逐一对齐用户给的链接、聊天、报价、照片/视频、平面图、权属或授权材料、合同草稿与该单元、发布者、日期；有冲突则保留两种说法，不拼接成一个“已确认”条件。缺口按同一核查方法补证据。

默认使用宿主 agent 已获准的搜索、浏览和文档工具。按[路线/POI API、运营方时刻与票价替代](references/routing-guide.md)选实际可用工具，没有浏览器UI不能成为停止全部路线工作的理由。提供的只读助手支持地理编码、步行路网、附近POI和柏林公交，须遵守联网批准及服务政策。逐项区分指定时刻行程、非时刻化路网模型、时刻表组合和缺失段，不把参考估计升级成已核高峰通勤。不自动联系房东/中介、预约、发送身份或财务资料、交定金、签约或提交申请。答复避免暴露现住户和用户的非必要个人信息。

## 候选的核查顺序

使用[候选与证据模板](references/candidate-record.md)，每个房源先确认：

1. **是不是同一套、同一期条件：**地址精度、楼栋/单元或公开房源编号、楼层、面积口径、户型、照片归属、发布主体、报价与更新时间。重复房源、不同装修/朝向/楼层、历史价格不得合并。
2. **是否违反硬条件：**入住日期、人数、宠物、无障碍、通勤、月度费用、初始现金及合同期限等，分别写满足/不满足/未知/资料冲突和依据。未知不能作满足；有明确不满足则不列为可用推荐。
3. **生活质量与现场风险：**采光、噪声、通风、潮湿/漏水、供暖/制冷、网络、供水电、楼宇维护、治安与交通以现场及可靠资料核对。图片、地图路线、平台标签只能提示，不是验房或高峰通勤实测。
4. **交易与费用：**先读[报价周期、签约现金、交通月票与购买情景计算](references/cost-comparison.md)，保留原币种/周期，避免重复计算已包含费用或订金，规则查实际司法辖区。`python3 scripts/normalize_costs.py <数据.json>`将已输入周/双周/季/年经常费用换成标明口径的月度预算等价，不核费用完整性或实际到期款。再按租赁读[租赁核查](references/rental-guide.md)；按购买读[购买核查](references/purchase-guide.md)。正式登记、授权、贷款、税务、学位或合同法律效果需要本地正式来源或专业人士确认，不能从宣传推断。

对**每个保留候选**，还要做[居住适配、出行与周边配套核查](references/enrichment-guide.md)：说明该单元的实际户型和适合/不适合的居住方式；从房源到用户常去地点分别给可行交通方式、门到门时间与费用；列出与用户生活相关的具名商圈及生活设施、步行/乘车时间和证据。不能只写“交通便利”“配套齐全”。多条路线的月费用可用 `python3 scripts/check_commutes.py <数据.json>` 复核，输入见[出行脚本说明](references/commute-input.md)；脚本不查地图。地图或挂牌不提供可核实数据时标未知并说明补查方法，不编造路线、店名或价格。

四态结论逐项附来源和日期。`资料冲突` 与 `未知` 需要不同的问题：前者要让相关主体解释差异，后者要索取具体证据。价格、状态、空置及政策资格注明核查日，行动前再次确认。

横向比较只在同一口径下进行：租房用相同入住时段、住期、人数和必要月费/签约现金；买房用相同成交价假设、融资状态、税费口径与持有成本；出行用相同目的地、时段、交通方式和每月次数。先剔除明确违反硬条件者，再说明剩余候选在户型、通勤、生活配套、费用、灵活性和证据可靠性上的取舍。优惠期价格不能和另一套的长期正常价格直接比；购房月供也不能与租金直接比成“哪套更便宜”。

按[推荐判定方法](references/recommendation-guide.md)给行动顺序：先处理硬条件，再核对证据和同口径成本，最后按用户偏好说明取舍。没有用户权重时不自行发明综合分；`值得看房` 不等于 `可以付款/签约`。

## 交付

通常给 3—5 个有依据的候选；不足时如实给更少，不拿楼盘介绍、失效页面或已知违反硬条件的房源凑数。先给行动结论：**值得看房 / 先补证据 / 暂不推荐**，以及决定原因；再列每套的**户型适配、到各目的地的方式/门到门时间/费用、具名生活配套和商圈**，然后列交易条件、来源、硬条件四态、住房与出行总负担、关键风险、2—4 个最有价值的问题和现场/签约前核查项。概述各区域和供给渠道的搜索覆盖及被排除的重要线索，不能把“未找到”写成“不存在”。

若身份/授权、收款主体、房屋可交易状态、重大缺陷或条款存在决定性疑点，先建议**暂停付款或签署**，列明要取得的证据；不要把在线检索当作交易安全保证。

需要公交/地铁通勤时，按[实际时段查询、班次、换乘与票价核查](references/transit-guide.md)执行；步行模型不能满足公共交通要求。
