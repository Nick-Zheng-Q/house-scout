# Actual-time public transport research

Use when bus, metro, tram, rail or ferry is required or compared. Read [tool access and provider policies](routing-guide.en.md) first. **A walking route, fare table, stop list, headway or station-pair average does not validate a public-transport commute.** Keep walking as a separate alternative. Do not replace an awkward short transit trip with walking and call the transit requirement met.

## Query and keep the returned evidence

1. Keep the user's original origin/destination and precision. A street-only listing remains street-level. Locate the correct station, direction and public boarding stop; same-name stops in another district are not interchangeable. If only station-pair data are accessible, label that scope; do not silently move the home to the station.
2. Submit the **local service date, arrival/departure time, timezone, and transit modes** to the actual available planner/API. A configured URL or an empty form is not a result. Save request parameters, response/source URL, retrieval UTC, actual returned dates/times and all legs. For arrival queries check the last arrival is on the requested local date and no later than the deadline, not merely that the request contained that date.
3. Retain each line/service/trip, boarding/alighting stops, platform/direction where returned, departure/arrival, change count, transfer walking and waiting, and service alerts/cancellation. A departures board for one stop alone does not establish a connection. Check that successive legs are physically and chronologically connected. Do not call missing transfer walking zero.
4. Route both outdoor access legs; indoor station access and platform changes require their own evidence or a clearly identified allowance. Walking-network models may supply an **access component**, never the bus/rail ride or an unobserved departure. If a connector is unverified, preserve the usable station-pair itinerary but not a complete door-to-door claim.
5. Query fares for the **obtained itinerary**: adult/concession, mode/operator, exact zones/distance, payment medium, time band and effective date. Prefer returned route fare; otherwise match the official tariff to the actual legs and cite that derivation. A generic month-pass price, walking distance as fare-kilometres, an advertised “from” fare or API `null` is not a trip quote. If price for the requested date is unpublished, keep the current priced reference and future-price gap separate.
6. Query the return independently when its date/time is known. Otherwise price a clearly conditional same-coverage return scenario, not a verified reverse journey. Monthly cost is `visits × (outbound fare + return fare)` only when both relevant fares/transfer rules are covered; compare passes separately with eligibility and coverage.

## Finish the public entrance and transfer checks

Agree the endpoint precision before scoring. If the user named a railway/MRT station, identify its **real public street entrance** from the operator's station/access map or an independently verified entrance address; state which entrance is used. Do not automatically add a train-platform deadline that the user did not request. Conversely, a nearby bus stop or underground metro platform is not that street entrance. If the user is catching a specific train, the deadline belongs at its platform with the required boarding margin; establish that separately.

Use the original full home address/building entrance. Preserve the original station and purpose when resolving an entrance; do not choose another station or stop to obtain a pass. If a planner truncates at a metro/bus platform, first locate the original railway station's public entrance, then query the full journey to that entrance address/coordinate. This may make the planner return the missing exit/footpath. Keep the station-name query as a comparison. Otherwise route the actual alighting location→verified entrance and home→actual boarding location, inspecting the returned path and snap locations against station layout/barriers. An outdoor road route beginning at an underground platform does not model stairs, gates or lifts.

For rail/metro access or changes, prefer the planner's explicit exit/transfer legs, official GTFS `pathways.txt` with actual traversal times, operator minimum-connection information, or a station-map-backed indoor path with a disclosed duration model. A station map alone establishes layout, not measured minutes. If a duration model is used, show path distance, levels/stairs/lifts, speed assumptions and added uncertainty; label it modeled, not operator-confirmed. An arbitrary “3minutes in/2minutes out” has no evidentiary basis. Check the actual departure after all access/transfer components: choose an earlier vehicle if needed, rather than subtracting unknown walking from a departure you already like.

Record component start/end locations and times, source kind (operator planner/schedule/official map/independent walk model), path length, date scope and uncertainty. The chronological total is home departure→final entrance arrival; a gap between legs is a **transfer interval**, not all waiting if walking occurs within it. Separate walking, waiting and any indoor component without double-counting planner footpaths. A route may be fully researched as a **planned/modelled commute** without being physically surveyed or a punctuality guarantee, provided no required connector is missing and the claimed endpoint precision is supported. Mark an unsupported allowance as a remaining gap, not a validated connector.

Keep the date of service and date of price evidence separate. A returned/official current tariff matched to the actual line, zones, payment and transfers can support a **current-priced dated plan**, with an explicit future-price caveat. Do not claim a fixed future fare when unpublished. Report `dated_route_complete`, `entrance_connections_complete`, `transfer_connections_complete`, `current_itinerary_fare_matched`, and `future_fare_confirmed` separately, plus the overall scope; an unknown future price is not a fabricated zero or an excuse to discard a genuinely complete current-priced plan. A different-date complete reference remains a reference, not an original-date completion.

## Outside the booking/data horizon

Do not change the requested day silently. Try it first. If unavailable, obtain a **separately requested, exact dated reference itinerary**, for example the next appropriate working day at the same local arrival time, and show both dates. A current dated reference can inform an estimate but cannot pass the original-date requirement. “Every10minutes” is headway evidence, not a dated departure. A live “next bus” is not tomorrow's08:30 service.

If the planner excludes transit because walking is shorter, record that response. A nearby boarding stop may help find a real alternative, but a station-pair diagnostic or a changed destination is a separate scope, not a successful original query. Explain whether the route is useful rather than manufacturing a pointless ride to increase pass counts.

## Local official GTFS when a planner is unavailable

Check the operator's current developer/download page and license; save the original ZIP, URL, download UTC and SHA256 outside the installed skill. Do not bulk-download entire countries when a local feed suffices. The [GTFS specification](https://gtfs.org/documentation/schedule/reference/) defines service calendars, exceptions, stop sequences, pickup/dropoff and frequency templates. Calendar coverage must actually include the queried day. **Also verify the publisher’s stated export date and publication horizon. A calendar extending beyond a narrower published horizon is not confirmation of those future trips; downgrade them to unconfirmed timetable records, even if the lookup finds active service IDs.** For example, a publisher promising rolling30-day data does not confirm December service merely because `calendar.txt` ends in December. If the export date is unknown or the sources conflict, record that gap and obtain a dated planner result or a reference inside confirmed coverage. A download timestamp does not reset the export-based window. Check route-specific completeness notices too; an empty lookup inside the nominal window still does not prove no service. The local script cannot verify this external publication promise.

`query_gtfs.py` is a **direct stop-to-stop timetable lookup**, not a routing engine. It reads a local authorized ZIP without networking. First inspect `stops.txt` and independently match stop IDs/directions; a parent station expands to actual children only. Use the feed's `agency_timezone` and correct date offset:

```sh
python3 scripts/query_gtfs.py /path/to/authorized-feed.zip --from-stop ACTUAL_STOP_ID --to-stop ACTUAL_STOP_ID --arrival 2026-12-01T09:00:00-05:00 --timezone America/New_York --output /tmp/scheduled-trips.json
```

The command checks active services/calendar exceptions, exact ordered stop times, pickup/dropoff permission, and previous-day times above24:00. It excludes all `frequencies.txt` templates and blank time interpolation rather than inventing precise departures. No result is not proof that no service exists. Published intermediate stop estimates (`timepoint=0`) remain flagged as estimates; a printed second is not a punctuality guarantee. It saves selected original stop-time rows and feed hash, but returns no fare, transfer plan or verified home access. For transfers obtain exact trips on each leg and sourced connector/wait times; do not sum disconnected rides or claim the latest-listed direct trip is a globally optimal route. Recheck disruptions separately.

## Evidence states for recommendations and tests

Report separately: **original-date transit itinerary**, **other exact-date reference**, **station-pair only**, **incomplete timetable components**, **access/egress**, **itinerary-matched fare**, and **conditional price scenario**. Full original-date transit validation requires a connected transit-containing itinerary at the requested date/time, supported access/egress at the claimed precision, and a matched fare. Keep route availability, endpoint precision and fare coverage as separate fields; no overall “pass” from an HTTP200 or successful arithmetic alone.

Prefer an earlier feasible trip with margin; do not count after-deadline alternatives.

The public planner can then query the original station's entrance street/number,but verify it is a real railway entrance rather than a nearby office building. ## Executable planner and schedule queries

Both network commands below use standard-library HTTPS, the same local shared pacing/cache as `query_routes.py`, and save request URL, retrieval UTC, raw JSON and a summary. For an independent evaluation pass a new `--cache-dir /tmp/this-run-only-cache` before the subcommand to both helpers; global service pacing remains shared, but prior raw-response caches are not read. `--public-locations` means public tests or authorized disclosure, not general permission to upload private addresses. Coordinates are **latitude,longitude**; use `--origin=-…,…` for negative values.

```sh
# Munich: first resolve the original building and an operator-confirmed public station entrance.
# Fill actual WGS84 latitude,longitude, not a railway centroid or an old example pin.
ORIGIN_WGS84="LATITUDE,LONGITUDE"
ENTRANCE_WGS84="LATITUDE,LONGITUDE"
python3 scripts/query_transit.py --public-locations --cache-dir /tmp/this-run-only-cache --output /tmp/mvv.json mvv --origin="$ORIGIN_WGS84" --destination="$ENTRANCE_WGS84" --arrival=2026-12-01T09:00:00+01:00
# Boston: official schedules; SAME trip ID at both stops, not two independent departures.
python3 scripts/query_transit.py --public-locations --output /tmp/mbta.json mbta --from-stop place-harsq --to-stop place-knncl --route Red --direction 0 --arrival=2026-12-01T09:00:00-05:00
```

MVV's normal public-web request is `/ng/XML_TRIP_REQUEST2` with `type_origin=coord`, `name_origin=lon:lat:WGS84[DD.ddddd]`, equivalent destination, `itdDate=YYYYMMDD`, `itdTime=HHMM`, `itdTripDateTimeDepArr=arr`, `outputFormat=JSON`. The adapter preserves all transfer footpaths, returned fare products and warning messages. It independently flags late/wrong-date alternatives; an API can return a late trip alongside a valid one. Check resolved addresses and station entrances. This website interface is not a guaranteed supported commercial API; recheck the [MVV public planner](https://efa.mvv-muenchen.de/) before use.

MBTA's [official V3 specification](https://api-v3.mbta.com/docs/swagger/swagger.json) documents `/stops`, `/schedules` and `/services`. Resolve stop IDs using `/stops?filter[route]=Red`, including `parent_station` and direction. The adapter requests a90-minute window, checks matching trip/stop sequence/pickup/dropoff and labels `timepoint=false` publisher estimates. It exposes `links.next` rather than silently claiming complete pagination. For a chosen trip, read its service relationship and `/services/{id}` to verify `start_date`, `end_date`, `valid_days`, `added_dates` and `removed_dates`; get `/alerts` for its stops/route/date. This is a **station-pair result**, with fare and home/platform access still separate. To compare a direct surface bus when metro entrance paths cannot be established, discover nearby stops with `/stops?filter[latitude]=LAT&filter[longitude]=LON&filter[radius]=0.005&filter[route_type]=3`; MBTA radius is in **degrees, not metres**. Use `/routes?filter[stop]=STOP_ID&filter[type]=3` to discover routes, check route direction names and the actual opposite-side stops, then run the same-trip query for the selected bus route. Resolve real station entrances via `/stops/{parent_id}?include=child_stops` and location type, rather than treating the station parent centroid as a door. This is a genuine alternative mode, not a walking substitute; report any slower/earlier departure and compare usefulness. Do not retry a blocked fare/CDN host through a mirror. An independent primary source is MBTA’s own [website fare implementation](https://github.com/mbta/dotcom/blob/main/lib/fares/fare_info.ex), not a scraped mirror of the denied page. Verify the current commit, adult `subway`/`single_trip` entries and supported payment media; `lib/dotcom/trip_plan/fares.ex` maps route types to that product and `lib/fares/repo.ex` actually loads the data. Preserve commit SHA/date and code lines. This can establish a current operator tariff, not an effective-dated future price announcement or an observed station access time.

## Authorized cross-market API when the free path is insufficient

If the user already has an authorized Google Routes project and explicitly permits its billing, the [official transit API](https://developers.google.com/maps/documentation/routes/transit-route) accepts `POST https://routes.googleapis.com/directions/v2:computeRoutes`. No account creation or billing activation is authorized by this skill. Read the key from approved configuration into `X-Goog-Api-Key` in memory; never print/store that header. Use `Content-Type: application/json` and field mask `routes.legs.steps,routes.duration,routes.travelAdvisory.transitFare,routes.localizedValues.transitFare`, and a body such as:

```json
{"origin":{"location":{"latLng":{"latitude":51.5266,"longitude":-0.0982}}},"destination":{"location":{"latLng":{"latitude":51.5257,"longitude":-0.0875}}},"travelMode":"TRANSIT","arrivalTime":"2026-12-01T09:00:00Z","computeAlternativeRoutes":true,"transitPreferences":{"routingPreference":"FEWER_TRANSFERS"}}
```

Use the requested location's timezone converted to RFC3339, not the example UTC blindly. Official docs permit up to7days past/100days future, subject to supplied schedules/coverage. Inspect `steps[].transitDetails.stopDetails`, departure/arrival stops/times, line, all walking/transfer steps, and final egress; `arrivalTime` in the request alone is not verification. `travelAdvisory.transitFare` may be absent if any step's fare is unknown: then separately research the operator rather than fill0. Follow provider storage/display terms. This credentialed path is documented but **not live-validated here without credentials**.


## If an interactive browser tool is not listed

Check for an **existing** approved browser runtime instead of assuming browser interaction is impossible. In a Codex local desktop environment, `load_workspace_dependencies` can return the bundled Node executable/packages, including Playwright; verify both `require('playwright')` and an already-installed Chromium executable. Do not invent an MCP browser tool, hard-code this developer's machine path into a user installation, install packages/browsers automatically, or launch the user's signed-in browser profile.

Use `exec_command` with the discovered Node runtime and a short Playwright script: launch an isolated browser/context with `timezoneId` set to the destination's IANA zone (for example `Australia/Sydney` or `Europe/Amsterdam`), identify this agent honestly (for example `ChatGPT-User`), navigate to the permitted public planner, inspect visible labels/inputs, fill the **original** endpoints, select actual autocomplete matches, choose public transport and explicit date plus **arrive by** (not depart at), and submit. Read the visible returned itinerary, expanded transfer details and fare; save a screenshot, visible text, final URL, actions and retrieval UTC. Check actual returned clocks and timezone as well as the form: an Asia/Shanghai browser can shift a Sydney09:00 request to12:00 despite a plausible URL. A saved empty home page is only tool discovery. Accept necessary functional UI choices, not account creation, purchases or expanded permissions. Do not read internal keys/tokens/cookies or replace the site's authentication with copied app credentials.

Check robots/site policy and stop at authentication, CAPTCHA, explicit blocking or rate limits; no stealth plugin, proxy, forged identity or changed client to defeat a block. An API endpoint denial does not itself prove a distinct public UI is unavailable, but do not replay the denied endpoint to get around its restriction. If the page normally offers only **weekday and departure time**, report that exact scope; it cannot express a specific calendar-date arrival query. Different operators' controls and labels differ: inspect real controls rather than paste imaginary selectors. An API field in JS source is not proof the form supports it.

A denial has a resource scope: do not retry a denied font/analytics file, but its failure alone does not make an otherwise permitted public route form forbidden. A blocked core route/auth request or CAPTCHA is different: stop that path. Browser security errors such as ORB must not be disabled; if core scripts cannot load, record an unusable UI rather than invent a login requirement.

## Additional checks established during the remaining-city review

**Full planner connectors:** a dated full-address→verified public **street-mouth** entrance result can supply its own access/egress walks. Use the full returned walking leg, not a shorter generic stop-centroid route. Reconcile the actual arrival bay and public footway against the operator terminal map; two bays on the same connected public footway need not become an invented indoor transfer. A second walking model is not mandatory when this path is already supported. Real level changes, closed/private passages or a contradictory bay remain gaps. A numbered metro exit may mean the street mouth or the bottom of stairs: state which one; do not invent a platform deadline.

**Japan surface buses:** the public NAVITIME bus form uses `/bustransit/search` with actual visible `orvStationCode` and `dnvStationCode`; discover those codes from selected stop links rather than guessing from rail IDs or an older parameter format. Set the form's date and arrival controls, verify returned clocks, and expand the actual alighting stop/bay. Match Tokyu/Citybus adult IC versus cash rules on the operator fare page. Search the exact entrance POI through the full-address comparison form and retain its full egress leg. Entrance POI IDs are not sequential exit numbers.

**Boston doorway evidence:** [Cambridge GIS's city-owned repository](https://github.com/cambridgegis/cambridgegis_data) publishes AddressPoints, building outlines, sidewalks and private walkways.
